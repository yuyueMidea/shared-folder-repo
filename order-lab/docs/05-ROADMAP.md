# 05 · 从演示到真实系统的路线

## 一、推荐开发顺序

| 阶段 | 工作 | 验收标准 |
|---|---|---|
| 1 需求冻结 | 明确买卖家范围、退款政策、时效、价格规则 | 每个操作都有触发条件和失败解释 |
| 2 数据结构 | 用户、店铺、商品、SKU、订单、订单行、支付、包裹、售后 | 金额单位统一，历史快照不依赖商品现值 |
| 3 基础订单API | 创建、查询、取消、版本控制 | 并发下单不超卖，超时可恢复库存 |
| 4 支付适配 | 支付单、回调验签、幂等、主动查询、退款单、对账 | 重复回调不重复入账，未知结果可追查 |
| 5 拼单服务 | 团/团成员、成团截止、人数并发控制 | 最后一名并发参团不超员；失败仅退一次 |
| 6 履约服务 | 商家归属、包裹、物流轨迹、签收、自动收货 | 发货与退款竞争有确定结果 |
| 7 售后服务 | 订单行退款、退货、质检、运费、证据、争议 | 累计退款不超实付，售后可重入且可审计 |
| 8 平台能力 | 客服、风控、发票、营销、结算、监控、备份 | 可恢复、可追溯、可监测异常资金差异 |

## 二、建议后端数据表

users、shops、shop_members、products、skus、inventory_reservations、coupons、user_coupons、orders、order_items、payment_orders、refund_orders、group_orders、group_members、shipments、shipment_events、after_sale_requests、after_sale_items、return_shipments、reviews、order_events。

演示中的单个订单嵌套对象方便学习；生产存储应按职责规范化。订单行保留sku_id与名称/规格/价格快照，售后行关联order_item_id。单独支付表支持支付失败重试、多次尝试但最终仅一次有效入账。支付/退款金额为BIGINT分或受约束decimal，避免浮点。

## 三、必须由服务器负责的约束

- 不能相信前端传来的unitPrice、discount、total、buyerId或role，后端从可信目录和会话计算。
- 下单事务锁定/原子扣减库存并绑定优惠券；重复请求携带幂等键返回同一订单。
- 商家只能查看与操作所属店铺；买家只能访问自己的订单；每个接口校验身份与状态。
- 使用version或条件UPDATE阻止发货与同意退款同时成功；影响行数为0时返回409并刷新。
- 第三方支付回调验签、校验商户号/金额/币种/订单号，保存原始回调用于审计。
- 支付成功与成团成功事件采用事务消息或outbox，确保下游最终收到，消费者幂等。
- 定时任务持久运行，不能依赖浏览器打开；付款超时与迟到支付回调需要补偿策略。
- 退款处理中保留独立状态，只有支付机构确认成功才标记退款成功；退款失败支持重试与人工核对。
- 地址、手机号访问最小化，日志脱敏；生产不能像本演示一样把完整订单存到任意客户端。

## 四、边界扩展清单

1. 购物车跨店拆单：父结算单 + 店铺子订单 + 多条订单行，运费和优惠分摊要可逆。
2. 部分退款：按商品行计算可退数量/金额，防止多次申请超过实付；优惠分摊按分取整并处理尾差。
3. 多包裹：订单已发货不代表全部发出，按订单行维护履约数量。
4. 换货：退回、验收、新包裹出库与新物流，不能复用退款完成状态。
5. 先用后付、免拼：支付条件和成团规则另建策略，不在旧枚举里不断打补丁。
6. 自动确认收货、延长收货：写入autoReceiveAt并由定时任务推进，售后期间暂停或按规则处理。
7. 售后证据：安全上传、文件类型/大小校验、对象存储、权限与内容审核。
8. 多标签同步：至少storage事件同步与版本冲突提醒；真实多人操作必须以后端为准。

## 五、验收关注点

买家体验要覆盖“成功、失败、取消、超时、重复点击、刷新恢复、找不到订单”；商家体验要覆盖“当前状态已被他人改变、退款期间发货、单号错误、退货未收到”。资金验收不止看UI：支付记录总额、退款记录总额、订单实付、库存释放记录、券返还记录必须可对账。

本次交付可作为需求讨论、前端学习和后端替换的基础，不应直接承接真实资金与商品交易。
