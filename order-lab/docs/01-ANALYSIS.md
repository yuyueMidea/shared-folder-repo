# 01 · 拼多多订单模块拆解与本项目范围

## 一、理解边界与资料依据

订单不是“商品列表加几个按钮”，而是商品、价格、库存、支付、拼单、履约、售后、评价之间的协调对象。用户看到的是订单卡片，系统内部则需要保证每一次扣款、发货和退款均有明确前置条件和可追溯记录。

本分析基于公开消费者场景，并查阅拼多多官方帮助中心与消费者保障页面（2026-10-25）。官方帮助中心列出了发货、已成团未发货退款、未收到货、商品问题、优惠券和退换货等问题；消费者保障页面说明了真实发货与有效物流信息、质量/描述问题售后、退换货与平台介入等要求。以下数据库、状态机、分层方案均为本项目自主设计，**不是拼多多内部代码、数据表或完整现行规则的披露**。

参考资料：
- https://www.yangkeduo.com/home/help/
- https://www.yangkeduo.com/home/customer

平台规则可能调整，商品类别也有差异。本项目使用明确且稳定的演示规则，不把各类商品适用条件、审批时效或退款到账时间泛化成平台承诺。

## 二、参与者与职责

| 参与者 | 关注点 | 在系统中的动作 | 本项目实现 |
|---|---|---|---|
| 买家 | 买了什么、花多少钱、何时收到、如何退 | 下单、付款、改地址、收货、评价、售后 | 完成 |
| 商家 | 需要发哪些货、哪些售后需处理 | 查看订单、发货、审核、退货验收 | 完成，统一商家视角 |
| 其他参团买家 | 拼单价格与成团进度 | 加入拼单 | 场景模拟按钮 |
| 支付机构 | 扣款/退款是否成功 | 支付回调、退款通知、对账 | 本地即时成功模拟 |
| 物流服务 | 包裹实际走到哪里 | 揽件、运输、派送、签收 | 4次可控推进 |
| 平台运营 | 异常交易、投诉、规则执行 | 仲裁、风控、补偿 | 方案说明，不实现 |
| 定时任务 | 交易是否超时 | 未付款关闭、成团失败退款 | 浏览器时钟+重载补偿扫描 |

## 三、页面按用户任务拆分

### 1. 订单入口与列表

“全部”负责完整检索；“待付款/待成团/待发货/待收货”负责行动提醒；“待评价”是已完成但未评价的派生视图；“退款/售后”是售后记录视图，不能简单当成交易状态。

列表卡片需要店铺、订单号、商品与规格、数量、价格、状态、金额和操作入口。多个状态按钮不可全部无条件展示：未支付不允许发货；有审核中售后不能继续发货；已发货不能直接取消而应走售后流程。

本项目支持订单号/商品/店铺/收货人文本检索、店铺、近7/30天、金额或创建时间排序、每页5条分页、筛选无结果空态。顶部指标为全部数据的概览，不随搜索结果变化；标签计数也按全部数据统计。

### 2. 确认订单

从选规格到下单至少确认：SKU是否存在、库存是否足够、数量是否合法、购买方式、商品价格、券门槛、运费、地址和备注。不能只相信页面展示的合计。下单时再次算价并校验，记录价格与地址快照，否则商品调价或地址簿修改会影响历史订单。

本项目每单一个SKU，支持1–20件。商品满99元免运费，否则6元；优惠券门槛和免邮均按优惠前商品小计判断。拼单价格与单买价格分别存放在SKU，订单快照保存实际采用的单价。订单创建时预占库存与券。

### 3. 支付与拼单

支付成功解决“钱”的状态，成团成功解决“是否达到交易组团条件”。两者不能混成一个字段。单买支付后进入待发货；拼单支付后进入待成团，第二位参与者加入后才允许发货。

演示未付款30分钟自动关闭；支付后24小时未成团自动模拟全额退款。倒计时只是显示，最终行为由领域规则判断。关掉页面时没有浏览器后台作业，重新进入会补扫过期订单。

### 4. 商家履约与物流

商家发货填写快递公司和单号，订单从待发货进入待收货。物流轨迹是附属记录而非交易主状态：快递已签收不等于买家已确认收货。项目故意保留这一差异，签收后仍需买家手动确认。真实系统需要物流订阅、轨迹去重、异常揽收、拆包与自动收货任务。

### 5. 评价与复购

订单完成后允许一次评价，1–5星、5–300字。评价记录和交易状态分开，已评价仍可在演示售后期限内申请售后。本项目不提供追评、图片评价、匿名设置或再次购买按钮；用户可回到商品页重新选购。

### 6. 售后与退款

未发货：只允许仅退款。已发货/已完成：可申请仅退款或退货退款；是否同意由商家操作决定，并非申请即自动退款。

仅退款链：申请 → 审核 → 同意 → 模拟退款成功 → 交易关闭。退货退款链：申请 → 审核 → 同意 → 待买家寄回 → 填退货单号 → 商家确认收到 → 模拟退款成功 → 交易关闭。审核中可撤销；商家拒绝必须说明原因，可再次申请，旧申请保留到历史。

所有退款为订单实付全额，包含原订单运费；这只是教学定价策略，不代表真实商品退运费规则。没有部分退款、退款到账失败、退货运费险或仲裁。本项目将收货后的售后申请窗口设为15天；真实接入要由后端根据商品与平台规则判断。

## 四、为什么需要多维状态

| 维度 | 示例 | 不能替代的内容 |
|---|---|---|
| 交易 | unpaid / grouping / toship / shipped / completed / closed | 表示交易生命周期 |
| 支付 | unpaid / paid / refunded | 关闭订单可能从未支付，也可能已经退款 |
| 拼单 | waiting / success / failed | 付款不等于成团 |
| 售后 | pending / returning / returned / refunded / rejected / withdrawn | 处理期间保留原交易阶段 |
| 物流 | 节点时间线 | 签收不自动等于交易完成 |
| 评价 | null 或 review对象 | 已完成还可能待评价 |

例如“待收货 + 已付款 + 售后待审核 + 物流运输中”完全可能同时成立。若把它压缩成一个“退款中”字符串，就难以知道撤销售后后该恢复什么状态，也无法正确显示物流。

## 五、本期取舍

为了让项目真正可下载即运行，不引入Sass、Bootstrap、组件库、图标包、Pinia或后端服务。Vue reactive足以承载单人演示；样式为普通CSS，路由使用Hash，静态托管无需重写规则。纯领域函数可用Node内置测试直接验证，不把规则埋在按钮回调里。

范围不追求复制拼多多的所有页面和营销入口，重点是可学习、可调试、可替换后端的订单闭环。真实生产系统还需权限、事务、并发、资金核对、日志存储与风控，其复杂度远高于本地模拟。
